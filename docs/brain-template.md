# The brain template

`henxels init --template brainpick-brain` scaffolds a [brain](brain.md):
the `_brain/` folder with its five memory types, a henxels contract that
enforces the brain format, a first skill that teaches the agent how to use
it, and a pointer back here. It is the fastest way from an empty repo to a
brain that brainpick can compile, serve and federate — and the reason every
brain that starts from it shares the same conventions, so none of them has
to be migrated to a better standard later.

## Why the template lives in henxels

brainpick is a tool that *renders correctly formatted data*; it stays clean
of project-layout opinions. henxels is already a requirement — it is the
referee behind [Guarded writes](guarded-writes.md) and the freshness gate —
and it already ships use-case templates (`okf-llm-wiki`, `agentic-project`).
A third template is the natural home: the contract carries each rule's
`why:`, so the contract *is* the documentation, and the digest henxels syncs
into `AGENTS.md` puts those reasons where every agent reads them. The
division of labour: henxels scaffolds structure and enforces it; `brainpick
init` detects the bundle, mints an id and compiles ([Onboarding](onboarding.md)).
Two tools, one handoff.

The template is also a distribution channel: it is how a henxels user
discovers brainpick, and the links in its seeds land on this wiki.

## What the template scaffolds

```
_brain/
  index.md            generated by compile ([index] mode = "section"), never hand-edited
  log.md              the bundle's running log, date-sectioned, newest first
  knowledge/          semantic memory — evergreen concept docs
  skills/
    using-the-brain.md   the first skill: pull first, read order, grounding, subsidiarity, "not the truth"
    skilltree.md         generated from depends_on — edit the skills, never the tree
  journals/
    index.md             what a journal is and how the month rolls
    YYYY-MM.md           the current month — a ## YYYY-MM-DD section per day, newest first
    archive/YYYY-MM.md   earlier months, moved here by the agent on the first entry of a new month
  raw/index.md        undistilled source material — greppable, indexed, excluded from the compiled brain
  vision/index.md     the northstar as a book; unlinked chapters are invisible
  plans/index.md      decided work only
_todo.md              parking lot — project management, beside the brain
_temp/                scratch — gitignored, always excluded
brainpick.toml        shared policy, committed: [bundle] root = "_brain", exclude = ["raw/*"], [brain] format = 1
brainpick.local.toml  machine-local endpoints — gitignored, never committed
henxels.yaml          the contract below
```

## The rules

Each is a henxel in the scaffolded `henxels.yaml`; the `why:` text is what
the digest shows the agent.

**Structure**

1. One brain, one bundle root — `_brain/`. Agents navigate the *compiled*
   artifacts, so the brain must be fresh before every commit:
   `brainpick compile --check-fresh` runs as a `run_before_commit` gate.
   Stale artifacts lie to agents ([Compile pipeline](compile-pipeline.md)).
2. Folders are memory types, one job each, nothing replicated across layers
   ([Data flow architecture](data-flow-architecture.md)); `raw/` beside
   them is source material, not memory.
3. Skills form a dependency tree: `depends_on` in frontmatter,
   `skilltree.md` generated from it.
4. Work areas may live inside the brain (catalogues, small scripts); a
   per-folder `allowed_filetypes` gate says what counts as brain material
   (`.md .txt .py .json .yaml .toml`). brainpick indexes the markdown; the
   rest is allowed but invisible to the graph.
5. Scratch is `_temp/`, always — gitignored, and in brainpick's
   always-excluded set rather than trusting config `exclude`.

**Document conventions**

6. OKF frontmatter on every concept doc: `type` required, `title` and
   `description` expected; a description containing `: ` is quoted.
7. Freshness is explicit: `timestamp` is bumped whenever a doc changes
   (`bump_updated_on_change`).
8. Reserved files stay frontmatter-free: `index.md` and `log.md`; the root
   `index.md` is compile-managed.
9. Every doc is reachable: `referenced_in` gates make an invisible doc *fail
   the check*, not rot.
10. Every link lands in the bundle: `rooted_links_resolve` and
    `links_resolve` — no ghosts hiding.
11. Kebab-case everywhere.
12. One journal file per month, `journals/YYYY-MM.md`, a `## YYYY-MM-DD`
    section per day, newest first, no frontmatter
    (`filename_matches_regex`, `no_frontmatter`, `log_headings_are_dates`).
    Entries point to what they changed, never restate it.
13. Only the current month stays at the top of `journals/` (`max_files: 1`
    with the index excepted); earlier months live in `journals/archive/`.
    The roll is the agent's act — the first skill teaches it, the check
    blocks a commit that forgot it. It is deliberately not a brainpick
    command: the engine does not know the layout
    ([Structure agnosticism](structure-agnosticism.md)).
14. Archived months keep the same shape, untouched.
15. `raw/` is orderly, never a dump: kebab-case names, listed in
    `raw/index.md`, a wider filetype list (`.csv .html .pdf .png …`), no
    frontmatter or links required. `brainpick.toml` excludes it
    ([bundle.exclude](reference/config/bundle-exclude.md)) so it never
    drowns the distilled layers — grep it to ground or to distil.

**Process**

16. Shared policy committed, machine-local config never — and no credentials
    anywhere (`no_secrets`).
17. Generated artifacts are marked and regenerated on commit; edit the
    source, never the output.
18. Deletion is deliberate: blessing required, removed lines count; near-
    duplicate files are warned about.
19. The rules live in one contract file and editing it is the only
    sanctioned escape; `--no-verify` is a genuine emergency only.

Two rules are principles rather than checks and live in the first skill:
[Grounding](grounding.md) (every claim says where it came from) and
[Brain subsidiarity](brain-subsidiarity.md) (the closest brain wins, update
both, duplicate or point). Several brains reach one agent through
[Federation](federation.md) — the registry the `[brain] audience` and
`brain://` links assume.

## Fixed for life versus cheap to iterate

Brains are committed markdown owned by their users; brainpick never
rewrites them and henxels only checks them. So a later change hurts in
exactly one of three ways, and the design puts the volatile parts where the
hurt is cheapest:

| A change to… | Who hurts | Recovery |
|---|---|---|
| how brainpick *reads* the bundle (indexing, ranking, overview order) | nobody — artifacts are disposable | recompile |
| the henxels contract (a rule gets stricter) | the next commit of a brain that pastes the new rule in | contracts are copied at init; old brains keep theirs until someone updates it |
| the on-disk shape of content (folder names, frontmatter keys, link syntax) | every brain, in committed content, and every other brain that links in | a migration |

Only the third row is a corner, and four things sit in it — chosen once,
kept minimal:

- **The root name `_brain/`.** Part of every cross-brain address. Fixed.
- **The five memory-type folders and their semantics** (plus `raw/`).
  Sufficient by construction: a new memory type is a `type` value or a
  sub-folder, never a seventh sibling. Adding is cheap; renaming is not —
  and note that this corner is the *template's*: brainpick never reads a
  folder name, so even a rename would break cross-brain links, not
  compilation ([Structure agnosticism](structure-agnosticism.md)).
- **The brain-format frontmatter keys** (`depends_on`, `export`). Few and
  boring, optional on arrival, never renamed — deprecate by adding. Human-
  read provenance is inline prose, not a key, precisely so the key set stays
  tiny ([Grounding](grounding.md)).
- **The `brain://` link syntax.** Slug-then-id, id authoritative, so a
  rename never breaks a link ([Brain subsidiarity](brain-subsidiarity.md)).

Everything else — retrieval ranking, the skill text, which checks warn
versus fail, the journal filename regex, the `type` taxonomy, every
generated file — is engine-side, contract-side or regenerated, and can
change between releases without touching a brain's history.

## Migration, when the format does change

`[brain] format` ([brain.format](reference/config/brain-format.md)) is the
stamp. A later format changes committed bytes only through
`brainpick migrate --to N`: a deterministic rewrite with a dry-run diff that
bumps the stamp, landing as one reviewable commit that henxels' deletion
blessing makes visible. Every earlier format stays servable through an
adapter, never a refusal. Without the stamp, every future change would be a
guess; with it and a migrate command, an architectural change is
*mechanical* instead of *manual* — the difference between release notes and
nobody upgrading.

## Making sure the docs are read

Nobody reads documentation voluntarily, agents least of all. What an agent
loads without being asked: `AGENTS.md`, Agent Skills (the description is
always in context, the body loads on match), MCP tool descriptions, and the
`hint` brainpick puts in every tool payload. Everything else is a deliberate
call away. The rule: **a doc that must be read is exactly one hop from an
always-loaded surface, and the hop is a call the agent is already making.**

The funnel, outermost first:

1. `AGENTS.md` — the henxels digest (each rule's `why:`) plus brainpick's
   compile report block, which for a brain adds "read
   `skills/using-the-brain.md` before writing."
2. The shipped Agent Skill ([Agent integrations](agent-integrations.md)) —
   its description is the trigger, its body the pointer to the first skill.
3. `brain_overview`, the call every session starts with — lists `skills/`
   first and carries the same hint ([MCP tools](mcp-tools.md)).
4. The brain's own `skills/` — retrievable procedural memory that links on
   to `knowledge/` and to this wiki.
5. This wiki — canonical, deepest, reached only by link.

Two consequences. A brain `skills/` doc and a harness-loaded Agent Skill
are different surfaces with the same name; the strongest guarantee
available is to make them the same file — a skill with `export:
agent-skill` in its frontmatter is written out as `SKILL.md` by
`brainpick integrate`, a marked, regenerated artifact, and
`using-the-brain.md` exports by default. And because the funnel is
description-driven, a skill's `description` decides whether its body ever
loads: the template's seeds are written as triggers ("Use when…"), not
summaries.

## Status

The format is specified ([Spec: brain format](reference/spec/brain-format.md))
and both engines read `[brain]`. The template ships in henxels
(`henxels init --template brainpick-brain`, documented in
[henxels' brainpick brain starter](https://github.com/benquemax/henxels/blob/main/docs/brainpick-brain-starter.md)),
and [brainpick init](reference/cli/init.md) recognises the result in place —
config at the repo root, bundle in `_brain/` — in both engines. Skills are
in ([Skills](skills.md)): `type: skill`, `depends_on` edges, `tools`,
`skilltree.md` generation, the overview listing skills first and
`brainpick skill new`. The template still writes `type: playbook` for its
first skill — a `playbook` is a how-to for humans and is *not* a skill to
the engine — so until henxels' next release retypes it, a brain scaffolded
today needs `type: skill` on its agent-facing procedures by hand. Still to come:
the Agent Skill export and `brain://` link extraction.
